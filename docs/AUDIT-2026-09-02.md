# Audit — Now Spinning site generator, live site, and agent flow

_Date: 2026-09-02. Scope: `site/build_site.py`, `site/qa.py`, the live site at https://music.hively.dev, and the Hermes cron flow that produces editions. Written as an exploratory audit; nothing was changed._

Every finding below has an ID (`D-*` data/flow, `R-*` rendering bug, `C-*` cohesion, `M-*` mechanics). Use the IDs when reporting what was fixed.

---

## 1. How the system is actually wired

Three copies of this project exist on the host. They are not identical.

| Location | Role | State on 2026-09-02 |
|---|---|---|
| `~/repos/prog-jazz-discovery` | Shareable repo | Scripts identical to live. SKILL.md is the generic version and **does not include the site-edition step**. |
| `~/.hermes/skills/media/prog-discovery-weekly/` | Skill Hermes loads | SKILL.md has drifted: `author: GregoryCloud`, description mangled to "Use when working with prog discovery weekly — Use when running… .." (the SKILL.md regeneration bug already noted twice in git history). Has one extra bullet for the site step. |
| `~/.hermes/prog-discovery/` | Live workspace | `state.json`, `draft.json`, `attribution.jsonl`, and `site/{build_site.py,qa.py,data/,out/}`. This is what builds the website. |

Serving: Caddy, `root * /var/www/music`, `file_server`, `Cache-Control: no-cache, no-store, must-revalidate`. Deploy is a plain `cp -r out/* /var/www/music/`.

### The Monday flow (cron job `prog-discovery-monday`, `0 9 * * 1`, model `glm-4.7-flash` on `zai`)

1. **Phase 1 — playlist.** Harvest, `pipeline.py verify`, `pipeline.py publish`. Battle-tested; two real runs.
2. **Phase 2 — research.** Pin the exact article URL per track, collect quotes, research the featured scene's genealogy, HEAD-check a Bandcamp/website URL for every new artist, append to `site/data/artists.json`.
3. **Phase 3 — site edition.** Write `site/data/<date>/tracks.json` (Spotify fetch) and `edition.json` (sources, 38 blurbs, 38 fine genre tags, theme paras, deep dive with family trees). Run `build_site.py`, then `qa.py`; deploy only on exit 0.
4. **Phase 4 — deliver** to the DM: playlist URL, count, blurbs, edition URL, QA proof.

**D-1. Phases 2–4 exist only in the cron prompt** (`~/.hermes/cron/jobs.json`), not in SKILL.md and not in this repo. The repo does not document how editions are made. Anyone reading the repo cannot reproduce the site.

**D-2. Phases 2–3 have never run unattended.** Both live editions (2026-08-29, 2026-08-31) were authored in interactive sessions on 2026-09-02. The first automated Monday is the first real test of a flash-tier model writing a 38-blurb, fully-sourced magazine plus a genealogical essay in one turn. Expect failures; the QA gate will catch structural ones only.

**D-3. Skill drift.** Repo SKILL.md ≠ installed SKILL.md (author, description, site step). Decide which is canonical and sync.

## 2. Data / pipeline bugs

**D-4. Lane data is read from the wrong place and will corrupt older editions next Monday. (Highest priority.)**
`load_all()` in `build_site.py` obtains each track's lane by reading `~/.hermes/prog-discovery/draft.json` — a single file that only ever holds the *current* week — and applies it to *every* edition. `main()` rebuilds every edition page on every run (the docstring's "edition pages never regenerate" is false). Consequence: when week 3 is published, `draft.json` becomes week 3, and the 2026-08-31 page will rebuild with an empty Spotlight, no Editor's Pick starbursts, and its four Zeuhl tracks silently dropped back into the shelves. `qa.py` will pass.
Fix: persist `lane` per track into each edition's `tracks.json` (or a `lanes` map in `edition.json`) at authoring time, and have `load_all()` read only from the edition directory. Backfill 2026-08-31 from the current `draft.json` before it is overwritten. Add a `qa.py` check that every track has a non-empty lane.

**D-5. Deploy never deletes.** `cp -r out/*` leaves retired output live. `/var/www/music/genres/` (a page the generator explicitly retired) is still being served. Use `rsync -a --delete out/ /var/www/music/` or clean explicitly.

**D-6. Repo examples are stale.** `site/examples/edition-2026-08-31/edition.json` predates the live file (live has `art`, `art_album`, `root_art` on tree nodes and longer notes). There is also a nested duplicate `site/examples/edition-2026-08-31/2026-08-31/`. Refresh or remove.

**D-7. `templates/state.json` `notes` still says "feedback 2"** although the feedback lane was replaced by wildcard.

**D-8. `qa.py` tests structure, not rendering.** It passed on every visual bug below. Add cheap checks where possible (see R-1, R-2, D-4).

## 3. Rendering bugs on the live site

Observed at 1440px and 390px with headless Chromium.

**R-1. Duration badge clips artist names.** The `.hype` time sticker (e.g. "14:31") is absolutely positioned over the bottom-left of the sleeve and overlaps the first characters of `.spine .artist`. Live examples: "ubilis" (Volubilis), "ar and The Deception" (Lunar and The Deception), "Used to Cut the Grass", "npan A", "l Vantage", "e Murray", "trum Orchestrum". Affects roughly a third of all sleeves.
Fix: move the badge onto the artwork corner (top-left or bottom-right of the `<img>`), or reserve left padding on `.spine` equal to badge width.

**R-2. Handwritten quote overflows the sleeve.** `.hand-note` (Caveat) on EYRE LLEW in the Post-Rock crate renders across the neighbouring two sleeves. The 38-char guard in `sleeve_html()` is not enough because Caveat is wide and the note is not clipped. Fix: `overflow:hidden; max-width:100%; white-space:nowrap; text-overflow:ellipsis` on `.hand-note`, or drop the note to two lines inside the sleeve.

**R-3. Family-tree connector renders as a stray "L".** The `└` glyph in `.tree-items li` floats detached from its row and looks like a typo. Replace with a CSS pseudo-element border (`border-left` + `border-bottom` on `li::before`) so it aligns with the thumbnail.

**R-4. Mobile: one sleeve per row at full width.** `.sleeves` is `repeat(auto-fill, minmax(158px, 1fr))`; at 390px the crate's padding leaves one ~350px column, so each cover is a full-screen square and the edition page is an enormous scroll. Target two columns below 640px (`minmax(140px,1fr)` plus smaller crate padding, or an explicit `grid-template-columns:1fr 1fr`).

**R-5. Near-empty crates.** A shelf with one or two tracks still draws a full-width wooden crate with one sleeve in the corner (Zeuhl & Canterbury: 1 track; The Fringes: 1 track). Zeuhl is empty precisely because its tracks were lifted into Spotlight. Options: don't render a shelf with < 3 items (fold into the next shelf with a note), or size the crate to its contents (`display:inline-grid` / `width:fit-content`).

**R-6. Mobile nav strip wraps to three lines** of tracked monospace ("THE LOG EXPLORE / CRATE-DIGGING, DOCUMENTED / NO ALGORITHMS · EVER"). Hide the two slogan spans below ~640px.

**R-7. Mobile edition header.** The editor note in Caveat at ~1.3rem, centered, occupies a full viewport before any music appears. Reduce to ~1.05rem, left-align, and clamp to two sentences.

## 4. Cohesion problems (why it feels unpolished)

The layout and aesthetic are right. The lack of polish is the absence of a system underneath the CSS. Measured from `build_site.py`:

| Metric | Value | Target |
|---|---|---|
| Web fonts loaded | 5 (Monoton, Alfa Slab One, Caveat, Courier Prime, Libre Franklin) | 4 (Monoton is masthead-only; keep it, but every other role must map to one of the remaining three) |
| Distinct `font-size` values | 41 | ≤ 8 (a named scale) |
| Distinct `letter-spacing` values | 19 | 3 (tight / caps-kicker / wide-masthead) |
| Hard-coded hex colors outside `:root` | ~40 | 0 (everything through tokens) |
| Inline `style=""` attributes in templates | 11 | 0 |
| Distinct section container treatments | 5 | 2 (one "editorial panel", one "crate") |
| `border-radius` values | 8 | 3 |

**C-1. No type scale.** Kickers alone use `.62/.64/.66/.68/.72/.78rem` with tracking `.26/.28/.3/.32/.34em` in different places. Define e.g. `--fs-kick:.68rem; --fs-meta:.78rem; --fs-body:.98rem; --fs-lead:1.15rem; --fs-h3:1.5rem; --fs-h2:clamp(1.6rem,4vw,2.6rem); --fs-mast:clamp(1.5rem,4.8vw,3.6rem)` and `--ls-kick:.3em; --ls-wide:.05em; --ls-tight:-.01em`, then delete every literal.

**C-2. Colors bypass tokens.** `#f2e7cf` (12×), `#3a2a1a` (12×), `#2c2012`, `#1c1108`, `#d8ccb8`, `#f5d67b`, etc. are used directly. Several are near-duplicates of `--paper`, `--aged`, `--text`. Promote them to tokens (`--cream`, `--rule`, `--panel`, `--panel-2`, `--gold`) and reuse.

**C-3. Five container styles for peer sections.** Spotlight = boxed panel with candy-stripe top; Deep Dive = mint left-rule box; front-page Theme = pink left-rule box; About = tilted paper card; Archive = unframed. Pick one "editorial panel" (suggest the Spotlight panel treatment with a single accent rule) and use it for Spotlight, Deep Dive, Theme, and Archive. Keep the tilted paper card only for About (it is the one intentionally physical object).

**C-4. Two neon accents with no rule.** Pink (`--neon`) and mint (`--neon2`) are both used for kickers, links, drop caps, borders, and the nav-active state. Assign: mint = interactive (links, buttons, nav-active, hover); pink = editorial mark (drop caps, section rule, starburst). Never swap.

**C-5. Sticker colors carry no meaning.** `tag_color()` hashes the tag string, so the same tag is green on a sleeve and yellow as a chip on Explore, and adjacent stickers clash at random. Map sticker color to **shelf** (7 shelves → 6 sticker tokens + tan), and use the same mapping for Explore chips.

**C-6. Duplicate headline on the front page.** Hero: "2026-08-31 · Zeuhl & Canterbury". Box directly beneath: "Zeuhl & Canterbury descendants". A dated playlist title is not a headline. Make the theme name the H2, demote the date/scene string to the kicker, and merge the hero and theme panel into one block (cover left, theme + lead paragraph + actions right).

**C-7. Shelf headers look unfinished.** The tilted divider tab is good; the tag list beside it is unstyled white body text. Style it as a mono meta line in `--text-dim` at `--fs-kick`, or move it into the tab under the count.

**C-8. Inline styles.** The whole Explore page header, the "new edition every monday" note, the edition-head kicker, the spotlight crate margin, and the empty-archive paragraph are inline. Move to classes.

**C-9. Explore genre pane is a single narrow column** with the edition link pushed to the far right edge; large dead space at ≥1000px. Constrain the row to ~44rem or make it a two-column grid at wide widths.

**C-10. Repeated kicker markup.** "EDITION 2 · 2026-08-31 · 38 TRACKS" is emitted three ways (front hero, edition head, explore) with different inline tracking. One `.kick` class.

**C-11. Spacing.** Section gaps range across `2.4rem / 3rem / 3.4rem / 2.2rem`. Use a 3-step rhythm (`--sp-2:1.2rem; --sp-4:2.4rem; --sp-6:3.6rem`).

**C-12. Drop cap inconsistency.** Deep Dive paragraphs use a pink drop cap on every paragraph (Z, C, T…), the front-page theme uses it once. Drop cap on the lead paragraph only.

## 5. Mechanics / maintainability

**M-1. `build_site.py` is 1,063 lines in one file** with CSS, JS, templates, and data loading interleaved. Fine for now, but the CSS should at minimum be a separate `site/style.css` string file loaded at build time so it can be linted and diffed.

**M-2. Inline JS handles both edition modals and the Explore view toggle** on every page; harmless but split by page if the file grows.

**M-3. Hash fragments on Explore** (`#g-<tag>`, `#a-<artist>`) are generated from raw strings; artist names with spaces or non-ASCII produce fragile IDs. Slugify.

**M-4. `qa.py` hard-codes `data/<edition>` next to itself** and assumes `out/` sibling; fine while the live layout holds, but it should accept a `--data`/`--out` override so the repo copy can be tested against `site/examples/`.

## 8. The skill itself: selection and theme (added after reviewing live state)

Grounded in `state.json`, `attribution.jsonl`, `candidates-week.json`, and the week-2 draft.

### How the weekly theme is chosen today

It is not chosen. `pipeline.py scene` returns `scenes[(week_counter) % 8]` from a fixed eight-entry wheel in `state.json`. The agent has no say; the website's "theme" essay is the agent writing about whatever the wheel landed on. Consequences observed in week 2:

- **S-1. The scene lane has no logic for what shape a scene should take.** Week 2's scene (Zeuhl & Canterbury) is a lineage, and tracing it from 1975 to 2026 was the right call; the owner liked it. The problem is that nothing *decided* that. The wheel gives a name; the skill says "any lane's sound, from one geography"; the only scene source is ProgArchives country charts, which return canon. So every scene, whether it is a lineage (history is the story) or a living scene like modern Scandinavian or Australian prog (what is happening now is the story), will come out looking the same: four catalog picks. Week 2 was correct by accident, and the next six scenes will be wrong by default.
- **S-2. The scene lane carries the most editorial weight** (Spotlight and Deep Dive on the site), which is fine and intended. It raises the stakes of S-1: whatever shape the scene defaults to is what the edition becomes.
- **S-3. The wheel is rigid and inconsistent.** Seven entries are geographies; "Zeuhl / Canterbury descendants" is a lineage. After eight weeks it repeats. There is no mechanism to bump a scene when the week's press actually hands you one (a strong Scandinavian release week, a label anniversary, a death).
- **S-4. `state.json.playlists` does not record which scene an edition carried**, so the history cannot be audited later.

### Selection rules that exist on paper but nothing enforces

- **S-5. Per-source caps were already broken in week 2.** Bandcamp 6 (cap 4), Progressive Subway 5 (cap 3), ProgArchives 5 (cap 3). Nothing in `verify` or `publish` counts sources. The Week-1 postmortem's central fix is unenforced.
- **S-6. Repeat rules are not checked by code.** `verify` never consults `played_tracks` or `played_artists`. `played_artists` is a flat set with no dates, so the "no artist within 8 weeks" rule cannot be evaluated; in practice it is "never", and only if the model remembers.
- **S-7. Max-4-per-subgenre is unenforceable at selection time** because tags are only written later, for the website. Candidates carry `lane` and `source` but no `tag`.
- **S-8. The obscurity gate is judgment-only.** Spotify does not expose monthly listeners, but `verify` already gets the track object and could fetch artist `followers.total` and `popularity` in one extra call per artist and print them. Today the model asserts "<500k" with no data.

### What is working

- Release-year mix is genuinely new: 23 of 38 tracks are 2026, 9 are 2025.
- Lane quotas were hit exactly (12/9/9/4/2/2).
- Ten distinct sources contributed; the reserve pool supplied only 4.
- TOTW auto-include produced 4 tracks as designed.

### Recommendations

1. **Give each scene an intent, and let the intent drive the picks.** (Owner decision 2026-09-02: a scene *may* be a history lesson, and a scene that traverses old and new is the most interesting kind. Do not split or ratio it. Do not force history where the scene doesn't have it.) Concretely: each wheel entry carries a `mode`, and the agent's scene harvest follows the mode.
   - `lineage` (e.g. Zeuhl & Canterbury, Italian symphonic, RIO): the story is descent. Picks span the decades: roots, middle, and where the line is now. Sources: ProgArchives for the tree, Bandcamp tags and current articles for the living branches. Week 2 is the template.
   - `living` (e.g. Scandinavia, Aus/NZ, Latin America, Eastern Europe today): the story is what that scene is producing now. Picks are current and previous-year releases; one root is allowed if it explains the sound. ProgArchives is for finding active bands, not supplying tracks.
   - `moment` (a label, a festival, a year, a city at a specific time): picks are whatever defines the moment, any age.
   - `microgenre` (owner addition 2026-09-02: e.g. jazztronica, dark jazz, math-rock, avant-metal, dissonant death, hyperpop-prog, kraut revival): the story is the sound itself. Picks are the records that define the sound plus who is doing it best now, any age. Sources: Bandcamp tags first, then RYM/ProgArchives subgenre pages and current reviews.
   The agent may argue a different mode for a given week if the harvest supports it, and must write the mode and one line of reasoning into `state.json.playlists[].scene_mode`. The Deep Dive on the site follows the same mode: family tree for `lineage`, "who is making this now" for `living`, timeline for `moment`, "what defines the sound" (the markers, the key records, the current practitioners) for `microgenre`.
2. **Make the wheel a default, not a law.** Keep the rotation, but add an explicit editor override step after harvest: if the week's sources cluster on something (a country, a label, a lineage, an instrument, a producer), the agent may name that as the theme instead and must write one line of justification into `state.json.playlists[].theme_reason`. Grow the wheel to 12 to 16 entries of mixed type (geography, lineage, label, era, instrument, microgenre) so it stops feeling like a country list.
3. **Record the scene and theme in state** on publish so history is queryable.
4. **Enforce the paper rules in `pipeline.py`.** In `verify`: reject tracks already in `played_tracks`; warn on artists in `played_artists` with the week they last appeared (store `{artist: week}` instead of a flat list); fetch artist followers/popularity and print them; count per-source and per-tag totals against the caps and print violations. In `publish`: refuse on cap violations the same way it refuses under 34 tracks. Add `tag` to the candidate schema so the subgenre cap can be counted.
5. **Archive stays at 2, unchanged.** The owner wants the history. The only nudge: when the scene is `lineage`, the archive picks should not duplicate that lineage (week 2's Dün was a Zeuhl record in the archive lane alongside a Zeuhl scene), so the two history slots reach somewhere else. No age quota on the edition overall; the mode system in recommendation 1 is what keeps every week from being a history lesson.
